# 电商售后异常诊断与工单协同 Agent

状态：开发方案，业务功能尚未实现，效果指标尚未测量。
日期：2026-09-02。参考代码基线：`ad09920`（本地 Cognida）。
求职方向：Agent 应用工程。基于 Cognida 二次开发，保留上游版权与许可声明。

## 1. 产品目标

面向电商售后运营，帮助用户发现退款异常、核对证据、制定处理方案，并在确认后生成内部工单。

代表问题：“最近两周华东地区退款率上涨，主要集中在哪些商品和物流渠道？依据是什么？帮我整理待处理工单。”

任务流程：澄清口径 → 查询数据 → 拆解异常 → 检索政策 → 形成有引用的报告 → 预览工单 → 用户确认 → 创建工单。

第一版支持中文、单店铺演示、订单级退款申请率、商品/地区/物流维度分析、模拟政策与内部工单。
模拟数据和模拟政策在界面、报告、README 中明确标识。继承平台租户边界。
交付版本包含 Supervisor、数据分析 Agent、政策检索 Agent 的协作；先实现单 Agent 基线，再接入协作并比较效果。
实际退款、外部工单平台、自动通知、库存预测放到后续独立需求。

## 2. 先固定业务口径

- 默认退款指标：某支付日期队列的已支付订单，在支付后 7 天内至少提交一次退款申请的订单数 / 该队列已支付订单数。
- 按订单去重；一笔订单多次申请只计一次；取消且未支付的订单不计入分母；分母为 0 时返回“不可计算”。
- 用户只说“退款率”且上下文无已确认口径时，先区分申请率、成功退款率与退款金额占比。
- 对比等长且都已完成 7 天观察的支付日期队列；数据水位覆盖整个观察期。未成熟队列只能输出标注为不完整的观察结果。
- 演示数据固定参考时点为 2026-08-31 00:00:00 Asia/Shanghai，当前队列为 [08-10,08-24)，基期为 [07-27,08-10)。
- 数据持久化时间约定为 UTC，展示与业务日期转换为 Asia/Shanghai；查询统一使用左闭右开区间。
- MVP 的退款商品维度限定每单一个商品；支持多商品订单时必须增加订单明细与退款明细，重新定义分摊口径。
- 明确区分退款率上升的“百分点”和相对增长百分比；金额使用定点数或整数分。
- 维度分析只声称关联或贡献，不直接声称因果。各维度可能重叠，商品贡献与物流贡献不相加。
- 同一互斥分组下可用 c(g)=本期组内退款订单数/本期总订单数−基期组内退款订单数/基期总订单数；其和等于总体率差，解释为描述性贡献。
- 小样本展示分母并降低结论强度；销量结构变化与组内率变化应分开观察。

## 3. 数据与知识设计

下表是新增演示业务模型的设计，落地前核对现有 schema。外部演示业务库与 Cognida 平台元数据区分配置。

| 数据 | 粒度与关键字段 | 用途 |
|---|---|---|
| demo_products | 商品；product_id、category、name | 商品维度 |
| demo_orders | 一单一商品；order_id、product_id、paid_at、paid_amount_cent、region、payment_status | 支付队列与分母 |
| demo_shipments | 每单一条演示履约记录；order_id、warehouse、carrier、promised_at、delivered_at | 物流异常证据 |
| demo_refund_requests | 一次申请；request_id、order_id、applied_at、status、reason、amount_cent | 去重计算申请率 |
| aftersales_tickets | 工单；tenant_id、ticket_id、action_id、order_id、status、evidence、created_at | 确认后落库 |

订单关联产品和履约记录；一单可有多次退款申请。查询先聚合申请，避免 JOIN 放大分母。
生成器使用固定随机种子、固定数据水位和版本号，建议首批约 5,000 笔订单，支持按参数调整规模。
生成正常、物流延迟集中、商品问题集中、销量结构变化、小样本、无退款、数据不完整等场景。
为每个场景计算独立的参考答案；场景标签与金标准只供评测，不能输入模型或进入知识库。

模拟文档包括退款处理政策、物流时效约定、售后处理 SOP、退款指标词典。
每份文档携带文档 ID、版本、生效区间和可引用段落 ID；按事件发生时间选择政策版本。
缺少适用政策时返回缺失证据，存在冲突且无法确定版本时请用户确认。

规划新增业务服务 `internal/service/aftersales/`，按 `handler → service → model ← repository` 组织。
平台持久化结构变更通过成对版本化迁移实现，并同步模型。演示业务库初始化另行版本管理。

建议工具契约（名称为设计稿，需在实现时注册）：

- `get_refund_metrics`：接收已确认口径、时间区间、过滤项；返回分子、分母、比率、数据水位和 result_id。
- `analyze_refund_segments`：接收结果引用与拆分维度；由确定性代码计算贡献、小样本标记和排序。
- `search_aftersales_policy`：复用知识检索，返回适用版本与段落引用。
- `prepare_aftersales_tickets`：接收订单集合、处理理由、证据引用，生成可审阅的草稿。
- 确认端点触发工单提交；模型不能用未经确认的工具参数直接写入。

精确计算、引用有效性、权限与写入约束交给代码；模型负责选择分析维度、补查、组织解释。
跨轮保存已确认口径、分析范围、证据引用和待确认操作 ID；不要仅依赖聊天文本恢复这些状态。
报告结构：统计口径、总体变化、重点分组、支持证据、待验证假设、建议、限制。

正式协作结构：Supervisor 管理任务和证据缺口；数据分析 Agent 使用领域查询/计算工具；政策检索 Agent 使用领域 RAG。独立任务可并行，有数据依赖时按结果补查。
交接契约包含 task_id、status、summary、result_ids、citations、missing_evidence；限制每个角色工具权限、迭代次数、时间与 Token 预算。首版禁止子 Agent 递归委派。
领域 RAG 包含条款级分块、版本与适用范围元数据、混合召回、重排和原文引用；逐项测量收益。单 Agent 与多 Agent 对比时共享同一工具和检索能力。

## 5. 工单与失败恢复

- 工单只写本项目内部数据库，操作身份与租户从可信请求上下文获取。
- 确认绑定不可变草稿内容和订单集合；用户改了范围必须重新确认。
- 状态至少包含 draft、awaiting_confirmation、confirmed、executing、succeeded、failed、expired、cancelled。
- 用业务唯一约束和事务保证相同 action_id + order_id 不重复创建；确认令牌一次消费本身不等于业务幂等。
- 提交响应丢失后按 action_id 查询既有结果；重试不得创建第二份工单。
- 确认凭证已消费但业务写入失败时，从持久化操作状态恢复，不能丢掉操作，也不能跳过授权。
- 到期、取消、跨租户、未确认的请求不能创建工单；执行前再次核验订单范围和当前状态。
- 工具返回结构化错误：参数问题、无数据、权限问题、暂时不可用；只对可恢复错误做有上限的重试。
- SQL 校验器需先确认实际调用路径，复现字符串与 UNION 等合法查询的误判，再决定语法树改造范围。

## 6. 评测与验收

第一批 30 个开发案例：正常分析 10、口径歧义 5、证据不足 5、工具错误 5、确认/幂等 5。
另建至少 20 个冻结测试案例，按场景模板划分，避免同一题改措辞后跨集合泄漏。
金标准包括参考查询/期望数值、允许结论、必需证据、禁止行为与预期业务状态。
动态恢复场景通过故障注入验证；确认流程需多轮测试，不能只用一问一答评测代替。

| 指标 | 判定方式 |
|---|---|
| 任务完成率 | 明确口径、正确数字、必要证据、目标产物均满足才计成功；要求澄清的任务按正确澄清验收 |
| 数值正确率 | 独立参考计算与查询结果比较，预先声明容差 |
| 证据支持率 | 校验引用存在、适用范围和版本；抽样人工判断结论是否由证据支持 |
| 轨迹合理性 | 允许等价工具路径，只约束必要依赖；不强求固定调用顺序 |
| 操作正确性 | 检查数据库最终状态；未确认写入和重复工单用确定性断言 |
| 运行成本 | 记录端到端耗时、Token、工具调用次数；人工等待时间单独统计 |

分别保留原版 Data Agent、售后专用单 Agent、售后 Multi-Agent 的结果。原版已有委派机制，不可直接将其标为单 Agent 基线；基线必须显式关闭委派并核对实际轨迹。
原版只比较双方都支持的分析任务；新增工单任务独立验收，不能用原版不支持工单来夸大提升。
固定代码提交、模型标识、提示词、数据/政策版本与缓存策略；清理评测间记忆污染。
预算允许时每例重复 3 次，报告均值和波动。先测基线，再设提升目标，所有简历数字来自保存的运行结果。

## 7. 开发顺序

时间仅为已有后端基础、每周能持续投入情况下的排期参考，按验收推进；详细任务见 [开发流程](aftersales-development-workflow.md)。

| 阶段 | 交付物 | 完成标准 |
|---|---|---|
| 第一阶段：环境、数据与案例（约 1 周） | 环境记录、指标词典、数据生成器、模拟政策、开发/测试案例 | 数据可重建；参考统计可复算；原有模型/工具链可调用 |
| 第二阶段：单 Agent 与领域 RAG（约 1～2 周） | 领域工具、单 Agent 基线、政策检索、引用报告 | 正常与歧义案例可演示；关键数字和政策能追溯 |
| 第三阶段：Multi-Agent 与工单（约 1～2 周） | 协作契约、补查/降级、工单状态与确认、幂等恢复 | 委派轨迹可观察；未确认不写入；重复请求无重复工单 |
| 第四阶段：对比与展示（约 1 周） | 冻结测试结果、消融实验、演示录屏、架构文档、简历条目 | 展示成功、澄清、失败任务；协作与检索收益可衡量 |

下一项可执行任务：核对启动条件与数据源接口，实现固定种子的模拟数据生成和独立参考统计，落地指标词典与第一批案例。
准备数据与契约不需要模型密钥；跑真实 Agent 基线时再配置模型，并记录实际调用成本。
