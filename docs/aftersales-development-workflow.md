# 电商售后 Agent 开发流程

状态：待执行清单；2026-09-02 更新。现阶段完成方案与局部静态阅读，尚未验证启动、实现业务模块或测量效果。
业务口径和数据模型以 [开发方案](aftersales-agent-plan.md) 为准。目标交付包含 Multi-Agent、领域 RAG、工单可靠执行和独立评测。
已有后端基础时可按约 4～6 周安排；这是排期参考，以阶段验收为准。

## 0. 环境与代码链路（1～2 个工作日）

- [ ] 核对 Docker、Go、Python、Node 与本地端口条件，按实际启动方式配置；只记录密钥变量名，不记录密钥值。
- [ ] 核对 compose 与依赖版本，尤其 compose 的 Milvus 2.5.4 与 Go 客户端 2.6 系列的实际功能兼容性，不能仅凭版本号判定可用或直接升级。
- [ ] 完成平台迁移与启动，验证登录、模型调用、一条只读查询、一份文档的入库检索；结束联调时停止本轮启动的服务。
- [ ] 沿 handler → 预设 → 执行循环 → 工具 → 数据库/检索服务阅读一次真实调用，保存可复现轨迹。
- [ ] 标出已有预设、子代理注册、工具注册、Result Store、确认机制、评测执行器的扩展点。

交付：启动记录、依赖问题清单、请求链路图、一个成功调用记录。
验收：能够重启复现查询和检索；明确失败发生在哪一层。模型接入受阻时，继续完成第 1 阶段的离线工作。

## 1. 业务数据、知识与评测样本（3～4 个工作日）

- [ ] 固定退款申请率、成熟队列、去重、时区、金额单位和分母为零等规则，形成指标词典。
- [ ] 设计订单、商品、物流、退款申请演示表与版本化初始化方式；为下一阶段工具定义明确查询粒度。
- [ ] 编写固定种子生成器，首批约 5,000 单，覆盖物流集中异常、商品集中异常、销量结构变化、正常及小样本场景。
- [ ] 编写独立参考统计，并用手算的小样本交叉检查；包含重复申请、跨期和未成熟队列。
- [ ] 准备模拟售后政策、物流 SLA、SOP，包含两个政策版本、适用范围、缺失证据案例与冲突条款。
- [ ] 创建 30 个开发案例和至少 20 个按场景模板隔离的测试案例；保存参考数值、相关段落、允许结论和操作状态。
- [ ] 给模型可见数据与评测金标准分开存放，报告中明确数据是模拟的。

交付：数据生成器、业务表定义、指标词典、模拟政策、参考统计与案例集。
验收：同一配置可重建同一数据集；独立参考计算可复算；金标准不会进入模型上下文或知识库。

## 2. 领域工具与单 Agent 基线（3～4 个工作日）

- [ ] 定义工具输入输出：退款查询返回口径/分子/分母/数据水位/result_id；维度分析返回贡献、小样本标记和证据。
- [ ] 将领域计算放到业务服务，再通过工具适配器暴露；工具输入校验、租户与数据源范围由代码保证。
- [ ] 复用已有检索作为初始能力，建立一个售后单 Agent，跑通澄清 → 取数 → 分析 → 检索 → 报告。
- [ ] 显式关闭委派，核对轨迹确认无子 Agent；原版已支持协作，不能把它直接当单 Agent 对照组。
- [ ] 规范错误类别并设置有限重试、工具超时、总步数及 Token 预算；结果过大时传引用和摘要。
- [ ] 对统计计算执行单元测试、真实演示库集成测试；新增 HTTP 接口时验证接口行为。
- [ ] 对开发集跑基线，保存输入输出、工具轨迹、模型配置、耗时、Token 和失败分类。

交付：领域服务与工具、单 Agent 预设、基线报告。
验收：至少完整演示正常、澄清、无数据三类任务；核心数字与参考结果一致，失败有可定位记录。

## 3. 领域 RAG（3～4 个工作日）

- [ ] 按政策条款分块，保留标题、条款 ID、文档 ID、生效区间和适用范围；处理表格及跨段条件。
- [ ] 复用混合检索基础，落地领域元数据过滤与版本适配，显式检查检索、重排服务是否实际启用。
- [ ] 分别测量向量召回、混合召回、加入重排后的结果；在相同语料和问题上比较。
- [ ] 对每条报告结论关联证据，区分“引用存在”和“引用支持结论”；无适用条款时输出缺失证据。
- [ ] 标注段落相关性，测 Recall@K、引用正确率和人工抽检支持率，记录检索延迟与调用成本。

交付：政策入库处理、领域检索配置、引用报告、检索对照结果。
验收：命中正确版本；缺失/冲突政策有明确处理；优化收益在开发集上可解释。

## 4. Multi-Agent 协作（3～4 个工作日）

- [ ] 注册 Supervisor、数据分析 Agent、政策检索 Agent，分别限定可用工具；首版不允许子 Agent 递归委派。
- [ ] 定义交接结构：task_id、status、summary、result_ids、citations、missing_evidence，并校验必需字段与引用归属。
- [ ] 先实现可追踪的顺序委派；正确后加入独立子任务并行，有依赖的政策/数据补查按顺序执行。
- [ ] Supervisor 汇总结论、检查证据缺口并触发有限补查；矛盾未解决时保留分歧和限制说明。
- [ ] 传任务所需上下文与结果引用，避免传整个对话和原始明细；建立总预算及子任务预算。
- [ ] 验证子 Agent 超时、无结果、格式错误、取消与父任务终止行为，确保并行任务能退出。
- [ ] 用与单 Agent 相同的模型、数据、工具和 RAG 配置做开发集对比；复杂度路由作为后续优化单独测量。

交付：三个角色、交接契约、协作轨迹、补查/降级机制、对照结果。
验收：能演示一次依赖结果的补查；能解释失败处理；同时报告完成率、耗时和 Token，接受部分任务无收益的结果。

## 5. 工单状态与可靠执行（3～4 个工作日）

- [ ] 设计持久化操作与工单模型、状态转移和数据库唯一约束；提交成对版本化迁移。
- [ ] 工具生成草稿，展示订单、理由、证据；确认绑定具体草稿版本，修改内容后重新确认。
- [ ] 复用确认接口，检查可信身份和租户；确认后的写入由业务服务执行。
- [ ] 将操作状态、工单写入与幂等结果协调持久化；处理确认已消费但业务事务失败的恢复路径。
- [ ] 验证重复确认、并发提交、响应丢失、过期、取消、越权和服务重启；以数据库最终状态验收。
- [ ] 同一租户的相同 action_id + order_id 最多创建一次，重试能够查询并返回既有结果。

交付：工单草稿/确认/提交/查询、恢复逻辑、故障注入测试记录。
验收：未确认不写入、重复请求无重复工单、失败可恢复且不跳过确认；测试数据与实际业务隔离。

## 6. 前端业务流程与展示（2～3 个工作日）

- [ ] 沿用现有界面，提供示例问题、业务范围、模拟数据标识与当前统计口径。
- [ ] 展示可观察的执行状态：分派任务、查询/检索、补查、生成报告；不把内部模型思维链当产品日志展示。
- [ ] 报告提供关键指标、维度图表、证据展开与不确定性说明；每个数字可追溯。
- [ ] 完成工单预览、确认、结果查询及错误提示，防止刷新或断连造成错误的成功提示。
- [ ] 浏览器验证正常、澄清、失败恢复三个完整流程；视觉润色在业务验收后完成。

交付：可演示业务界面、三个流程录屏。
验收：用户能理解当前进度、依据和待确认内容，后端操作状态与界面显示一致。

## 7. 冻结评测与面试材料（2～3 个工作日）

- [ ] 冻结代码、模型标识、提示词、语料/数据版本与缓存策略，按任务重置会话与记忆。
- [ ] 分开做两组实验：相同 Agent 的检索策略比较；相同工具/RAG 的单与多 Agent 比较。
- [ ] 冻结测试集上测任务完成率、数字正确率、证据支持率、延迟、Token；预算允许每例重复 3 次并报告波动。
- [ ] 工单用状态断言和故障测试单独验收；共享分析任务才用于原版对比。
- [ ] 保存失败案例；测试集用于最终验证，若根据其问题继续调优，需要新的独立测试数据验证。
- [ ] 整理架构图、三段关键代码、两个真实排错案例、运行方式、原始评测记录与实测简历条目。

交付：最终评测报告、演示材料、项目说明和简历内容。
验收：每个简历数字可追溯；每个技术亮点有实现和案例；能够解释方案取舍与局限。

## 执行纪律与今天的起点

每个任务按“定义验收 → 阅读扩展点 → 实现最小改动 → 必要测试 → 自查差异 → 记录结果”推进。
每阶段保留可运行版本与失败记录；数字效果来自真实评测；范围变化同步到开发方案。
当前优先：完成阶段 0 的环境/链路核对，并落地阶段 1 的指标词典、演示数据生成和参考统计。
本文件与方案位于仓库现有忽略规则中的 docs 目录，当前作为本地开发资料保存。
