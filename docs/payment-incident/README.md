## 下一步工作与验收标准

| 顺序 | 工作内容 | 验收标准 |
| --- | --- | --- |
| 1. 检索闭环 | 核对全部分块向量，测试 vector、BM25、hybrid 三种模式 | 支付超时、回调失败、状态不一致问题可返回相关证据，来源可追溯 |
| 2. 基线评测 | 用开发集的问题与必要证据评估检索；工具行为待接入后再评估 | 保存逐条结果、配置、耗时、失败案例和汇总报告 |
| 3. Token 统计 | 接入明确口径的分词计数，记录 tokenizer 或估算方法，回填现有分块 | 非空分块具有有效计数，估算 Token 与供应商计费 usage 分开记录 |
| 4. 混合 RAG 优化 | 比较单路与混合召回，按结果引入 Reranker、版本过滤及引用校验 | 固定评测集下记录优化前后质量与成本变化 |
| 5. 支付 MCP 工具 | 构建模拟订单、支付和回调数据，接入状态查询、记录查询、日志查询和回放工具 | Agent 根据工具证据诊断，参数校验与调用审计可检查 |
| 6. 审批与幂等闭环 | 实现待审批草稿、确认执行、参数变更审批失效、幂等查询与处置后验证 | 无审批不可执行，同一动作重复请求不产生重复副作用 |
| 7. 长期记忆 | 实现任务状态、服务事实、故障经验及验证、版本、有效期治理 | 对比有无记忆的工具调用次数，测试错误记忆对结果的影响 |
| 8. Agent Harness | 验证 Checkpoint、分类重试、上下文压缩、预算与幂等恢复 | 进程中断、工具超时、响应丢失后可恢复，保存轨迹与成功率 |
| 9. 简历与演示 | 整理架构图、业务演示、贡献说明及评测报告 | 每项功能和数字均可对应源码、日志或评测证据 |

## 后续量化指标口径

- **证据 Recall@5**：前 5 个分块覆盖的必要证据数 / 标注必要证据数，按证据 ID 去重，再按问题平均；无必要证据的问题单独评估拒答。
- **检索耗时**：按模式记录平均值、P95 和样本数，说明是否包含 Embedding 与 Reranker。
- **端到端成功率**：同时满足必要证据、预期结论和操作约束的任务数 / 总任务数。
- **未授权操作率、重复副作用率**：分别以越权尝试和重复请求为分母，报告计数与比例；有限测试为 0 不代表所有情况为 0。
- **记忆收益**：相同任务及配置下，比较启用记忆前后的工具调用次数，并报告错误记忆导致结果变差的比例。
- **中断恢复率**：故障注入后恢复完成且无重复副作用的任务数 / 注入任务数。

当前 20 条案例用于开发调试。正式量化前需增加独立测试集，避免反复调参后仅报告开发集结果。

## 检索基线运行

`evaluation/run_retrieval_baseline.py` 通过 Cognida 的统一检索 API 依次运行 `vector`、`bm25`、`hybrid` 三种模式。它只读调用 `/api/v1/knowledge/search`，并按返回片段中出现的 `【PI-KB-…】` 证据编号计算证据 Recall@5；不会上传开发集或变更知识库。

先从知识库列表取得「支付系统故障知识库」的 ID。若未开启本地 `DEV_MODE` 认证绕过，将登录后的 Bearer Token 放到环境变量中，避免写入命令历史或结果文件：

```powershell
$env:COGNIDA_TOKEN = '<登录后的 access token>'
python .\docs\payment-incident\evaluation\run_retrieval_baseline.py `
  --kb-id '<支付系统故障知识库 ID>' `
  --output .\docs\payment-incident\evaluation\results\baseline-$(Get-Date -Format yyyyMMdd-HHmmss).json
```

结果文件保留逐题命中、漏失证据、HTTP/API 错误、单题耗时、均值与 P95。没有必要证据的案例不纳入 Recall@5，后续应在 Agent 接入后单独检查其“证据不足时拒答”的行为。

### 2026-09-06 基线与 BM25 修复准备

首份开发集基线已保存至 `evaluation/results/baseline-20260906-145000.json`：vector 与 hybrid 的证据 Recall@5 均为 56.25%，BM25 为 11.25%。服务日志显示多数中文问题的 Milvus BM25 查询返回 0 条，随后走 MySQL 降级检索；这不是可接受的 BM25 验收结果。

修复配置已将 Milvus 升至 `v2.5.11`，并把 BM25 的 `text` 字段改为官方 `chinese` 分析器（jieba 分词）。**分析器属于集合 schema，不能原地修改**：应用该修复时必须先拉取新镜像，再以 `provision-milvus --recreate --reindex` 重建并回填集合。该命令会删除并重建现有向量集合，因此执行前必须确认已有 11 个分块可从 MySQL 回填，并在重建后重新运行基线；不要把更新镜像误认为修复已生效。

已于 2026-09-06 完成重建并回填 11 个分块，复测结果保存至 `evaluation/results/baseline-20260906-140100-chinese-analyzer.json`：vector Recall@5 为 56.25%（P95 251.74ms），BM25 为 55.00%（P95 16.43ms），hybrid 为 58.75%（P95 211.77ms），三种模式均无 API 错误。BM25 改善证明服务端中文分词已生效；hybrid 仅较 vector 增加 2.5 个百分点，下一轮应针对仍漏失的开发案例检查分块粒度与融合参数，而不是宣称该指标已达标。

## 演示约束

- `replay_payment_callback` 是有副作用的操作，必须先生成待审批草稿；未经确认不得执行。
