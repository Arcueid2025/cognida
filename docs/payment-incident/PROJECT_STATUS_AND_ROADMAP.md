# 支付故障核验平台：项目进展与开发路线

## 1. 项目目标

建设一个面向支付异常的辅助核验平台：用户输入订单号或故障现象后，系统从支付知识库中检索可追溯证据，提供核验清单；涉及补单、回调回放等高风险动作时，必须由人工确认并留下审计记录。

当前原则是：**先证据、后建议；无证据不自动处置。**

## 2. 已完成工作

### 2.1 运行与基础设施

- 已通过 Docker Compose 运行前端、Go 后端、Python 服务、MySQL、Milvus、Neo4j、Redis、MinIO 等依赖。
- 前端入口为 `http://localhost:8888`，Go API 健康检查为 `http://localhost:8080/health`。
- 已验证前端页面与后端健康检查均可返回 `200`。

### 2.2 中文检索能力

- Milvus 已升级至 `v2.5.11`，并将文本分析器改为中文分析器。
- 已重新创建支付知识库的 Milvus collection 与索引，并完成 11 个分块的重建。
- 已启用向量检索、BM25 检索和混合检索三种模式。

### 2.3 检索评测与基线

- 新增离线检索基线脚本：`evaluation/run_retrieval_baseline.py`。
- 脚本输出每条测试用例结果、证据 Recall@5、平均延迟、P95 延迟和 API 错误数。
- 已新增脚本单元测试并通过。

当前基线使用自建支付故障测试集；现有知识库规模为 **5 份文档、11 个分块**，测试集为 **20 条开发用例**，因此指标仅用于当前原型的横向对比，不能代表线上效果。

| 模式 | Recall@5 | 平均延迟 | P95 延迟 |
|---|---:|---:|---:|
| 向量检索 | 56.25% | 173.51 ms | 251.74 ms |
| BM25 | 55.00% | 11.48 ms | 16.43 ms |
| 混合检索 | 58.75% | 162.14 ms | 211.77 ms |

中文分析器修复前，BM25 Recall@5 为 11.25%；修复后提升至 55.00%。

### 2.4 支付故障核验台

已新增路由 `/payment-incidents`，对应“支付故障核验台”。当前页面支持：

- 输入订单号或故障描述。
- 选择单个知识库，或对当前可访问知识库执行检索。
- 固定使用混合检索，返回最多 5 条原始证据。
- 针对支付超时、`PAYING`、支付成功等关键词给出安全的核验顺序。
- 无检索证据时明确提示转人工处理，不会自动补单、回放或变更订单。
- 证据卡展示真实文档标题、相对匹配度与查询关键词高亮。

### 2.5 代码质量与验证

- Go 知识检索服务单元测试通过。
- 支付核验台前端单元测试 4/4 通过。
- Vue TypeScript 类型检查通过。
- Git 差异检查通过。

## 3. 当前能力边界

当前系统已经实现：

```text
支付异常描述 / 订单号
        ↓
混合检索（向量 + 中文 BM25）
        ↓
原始证据 + 核验清单
        ↓
人工判断
```

当前系统尚未实现：

- 自动读取真实订单、支付流水、回调日志。
- 支付故障案件创建、状态流转与责任人协作。
- 基于证据生成结构化处置建议。
- 补单、回调回放等动作的人工确认、权限校验和审计闭环。
- 大规模知识库、真实历史故障数据和线上评测。

因此，现阶段定位为“支付故障知识检索与人工核验原型”，而非可直接执行资金相关操作的生产系统。

## 4. 后续开发路线

### 阶段 A：检索质量与证据可读性

目标：让证据足够相关、可理解、可复核。

1. 扩充支付知识库、历史故障案例和标准答案标注集。
2. 持续使用 Recall@5、P95 延迟、错误率做回归评测。
3. 对混合检索接入并评估重排序策略；只有在指标提升且延迟可接受时才启用。
4. 增加查询改写、同义词与订单/渠道/状态等领域词识别。
5. 为每条证据增加文档名、片段编号、命中词、检索模式与来源跳转。

验收建议：评测集扩充后，定义明确的 Recall@5 与 P95 延迟目标；每次检索策略变更都必须与基线对比。

### 阶段 B：受证据约束的处置建议

目标：将“检索到什么”提升为“在证据约束下建议如何核验”。

1. 定义固定输出结构：故障判断、已知事实、待核验项、建议动作、风险提示、引用证据。
2. 建议中的每个关键结论必须绑定至少一条证据；无证据时只允许输出“信息不足，建议人工升级”。
3. 将补单、回调回放、关闭订单等列为高风险建议，只生成操作草案。
4. 保存用户问题、检索证据和建议版本，便于复盘。

### 阶段 C：支付故障案件流

目标：形成可追踪的人工处理闭环。

1. 创建案件实体：订单号、渠道、异常类型、优先级、状态、责任人、创建时间。
2. 保存核验结果、人工结论、附件和处理时间线。
3. 支持案件状态：待核验、处理中、待确认、已解决、已升级。
4. 将检索证据与处置建议关联到案件，保证后续可追溯。

### 阶段 D：受控操作、权限与审计

目标：在不直接扩大资金风险的前提下支持操作闭环。

1. 对高风险操作实施 RBAC 权限控制和二次确认。
2. 使用幂等键防止重复补单或重复回放。
3. 全量记录操作申请、审批、执行结果、操作者、请求 ID 和时间。
4. 先接入模拟订单/回调服务完成端到端验证，再评估真实系统接入。

### 阶段 E：稳定性与上线准备

目标：使项目具备可演示、可复现和可维护的工程质量。

1. 将检索基线评测接入 CI，指标退化时阻断合并。
2. 补齐接口测试、集成测试、异常场景测试与权限测试。
3. 完善数据脱敏、JWT/密钥管理、备份恢复与运行监控。
4. 编写架构图、启动文档、演示脚本和技术复盘。

## 5. 秋招项目化目标

在完成阶段 B、C 和部分 D 后，项目可定位为：

> 支付故障知识检索与人工核验平台｜Go · Vue 3 · Milvus · MySQL · Redis · Neo4j

建议简历表述必须携带评测规模，例如“在 20 条自建支付故障开发用例上”，避免将原型指标误写为线上指标。

可重点体现：

- 中文 BM25 分词与混合检索治理。
- 检索评测、回归基线与性能指标。
- 证据可追溯和高风险操作的人机协同设计。
- Go 服务分层、Vue 前端工作台、Docker 化多服务部署。

## 6. 下一项建议执行的任务

优先进入阶段 A：扩大评测数据并对重排序进行离线对比。只有证明重排序能提升 Recall@5，且延迟仍在可接受范围内，再将其接入支付故障核验台。
